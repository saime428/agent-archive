# v2.0 Tokenicode Workbench Closeout

The Tokenicode-style Workbench refresh is frozen as a completed visual product
slice. It keeps the existing Python core and static Workbench, and upgrades the
browser experience without introducing a frontend build system.

## Scope

Completed in this pass:

- resizable three-column Workbench shell
- light and dark theme support with persisted preference
- SSE browser chat path with public process cards
- conversation tabs and per-conversation menu actions
- saved conversation titles, rename, and delete APIs
- Markdown rendering for chat answers, code blocks, and tables
- compact resource dashboard with paged previews and click-to-expand detail
- safer startup defaults on port 8000 with port retry handling

The work intentionally stays on the current stdlib server and static asset
stack. No Vite, Electron, Tauri, Monaco, or database layer was added.

## Design Decision

The Tokenicode direction fits the product better than a landing-page style UI:
this app is a local coding workbench, so the first screen should feel like an
AI coding IDE, not a marketing surface. The refresh prioritizes dense working
panels, readable chat, persistent local context, and low-friction inspection of
runs, files, resources, and approvals.

## Known Limits

- The file editor remains a textarea.
- The legacy synchronous chat endpoint remains as a compatibility fallback.
- Resource detail views are still backed by local JSON files and in-memory page
  state, not a searchable database.
- The browser settings path is still read-only for secrets and high-risk config.

## Next Triggers

Only expand this slice when one of these becomes true:

- textarea editing blocks real use, then evaluate Monaco or CodeMirror
- static asset state becomes painful, then introduce a small frontend build
  system
- users need non-developer distribution, then revisit packaging
- resource lists become too large for local pagination, then add search/indexing
